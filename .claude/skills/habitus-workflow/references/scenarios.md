# 场景预期对比

这是整个审核流程里最能抓到主流程 bug 的一步。做法是：**对每个设计点，构造它会出现的场景，先写下预期，再让真实代码跑一遍，逐个对比。**

## 为什么放在读代码前面

读代码能查出「这一行写错了」，但很难查出「这个算法在某种日子规律下，行为和设计不符」。后一类问题的每一行代码单独看都没错，错在它们组合起来的效果。

实例（2026-10-30）：建预期时按历史间隔聚簇。天天洗澡的人漏过一天，历史里就有了「隔 2 天」，和「隔 1 天」连成一簇，时窗从此变成两天。此后再单独漏一天，就永远不提醒了。这段代码在之前几轮审核里都被读过，没人发现。最后是给 30 天数据写提醒预期时，算出来的结果和设计对不上，才暴露的。

## 步骤

### 1. 列设计点

从共享说明第 2 段拿到设计点列表。每个设计点改写成一句**可以被观测到的话**：

- 不好：「时窗应该合理」
- 好：「天天做的事，漏过一次之后，再单独漏一天，当天时窗末要问一句」

### 2. 按情况矩阵构造场景

对每个设计点，至少检查下面这些情况里**和它相关的**：

| 维度 | 情况 |
|---|---|
| 节奏 | 天天做 / 隔天 / 每周 / 不规律 |
| 缺失 | 漏一天 / 连漏两天 / 连漏很多天后停下 / 漏过之后再漏 |
| 恢复 | 停很久后回来 / 回来后又停 |
| 时刻 | 准时 / 晚了但做了 / 换了时间 / 周末晚做 |
| 观测 | 整天没有会话（没看到）/ 有会话但没做这件事 |
| 日历 | 工作日 / 周末 / 节假日 / 调休 / 出差 |
| 提醒 | 被提醒后做了 / 被提醒后没做 / 回答「这次不用」/ 名额已满 / 宿主没取 |
| 时间边界 | 跨零点 / 夜批前后 / 窗口开头和结尾 |
| 冷热 | 账刚建起来 / 账攒够了刚升档 / 账已稳定 |

规则：
- **一件事一个场景。** 不要让两个场景共用同一件事，否则一个场景的结果会改变另一个。
- **关键日子不贴窗口边。** 要留出足够的前置历史，以及结算所需的后续天数。
- **日程服从世界设定。** 出差、生病、节假日当天不应该出现与之矛盾的行为。
- 事件不够就加事件，宁可多几件事，也不要一件事背多个场景。

### 3. 先写预期

每个场景的预期写成表，**在跑代码之前存盘**：

| 场景 | 验哪个设计点 | 关键日子 | 预期 | 依据 |
|---|---|---|---|---|
| E1 维生素单漏 | 漏过一次后再单漏照常提醒 | 第 20 天 | 08:00 时窗末问一句 | 裁定 <n>、统一说明 §2.2 |

预期要写到能直接比对的粒度：哪一天、几点、建不建预期、问不问、结算成什么。

### 4. 选跑法（按成本从低到高）

1. **手算小例子**：几行数据，自己推出结果，再用单测跑代码。适合单个函数或算法。
2. **单测或属性测试**：把不变量写成测试，例如「序号不回退」「一条预期最多一条『说了』」「结算完的日子不再改」。
3. **合成数据回放**：用造好的多天数据跑真实整条链。适合涉及多天累积、跨层交互的设计点。
4. **真实数据回放**：本机真实会话转写，只读。适合检查「正常用法下会不会碰到」。

跑法必须是真实的代码路径，不能拆一半跑；涉及模型调用的，就调真实模型。

### 5. 逐个对比

| 设计点 | 场景 | 预期 | 实际 | 一致吗 | 不一致的原因 |
|---|---|---|---|---|---|

不一致时，按顺序排查：
1. **预期写错了吗？** 重读裁定原文。
2. **数据造错了吗？** 场景数据是否真的构成了这个情况。造错了立刻改数据重跑。
3. **代码偏离设计了吗？** 是的话进入第 5 步独立复现。
4. **设计本身有缺口？** 讲清楚，问用户。

### 6. 标出覆盖缺口

结构上出不来的设计点（例如需要的历史超出窗口），标「✗（结构上）」，并写清卡在哪。改用单测覆盖，或者记进待办。不要假装覆盖了。

## 修复后

每个修复落地后，重跑**所有受影响设计点**的场景，不只是出问题的那一个。只核对变化的部分：哪些场景的结果变了、变得对不对。上一个修复带出的回归，就是在这一步抓到的。
