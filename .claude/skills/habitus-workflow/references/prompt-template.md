# 提示词模板

执行流程第 0 步由主 session 写**一份**提示词文件，交给用户另开的执行 session。放在桌面 `~/Desktop/Habitus/experiments/<日期>-<条目>/提示词.md`，执行报告写到同一目录 `报告.md`。

写之前主会话必须已经：读完涉及的模块、盘点完全部落点、写死预期、按测试矩阵选好测试。提示词里每一句"代码现在怎样"都带本次读过的 `file:line`。

文件开头放一张表，写清每部分谁读、先后顺序：

| 部分 | 谁读 | 顺序 |
|---|---|---|
| 一、共享说明（按 brief-template.md） | 执行 session、codex 复核 | 先读 |
| 二、执行 | 执行 session | 读完一再读 |
| 三、codex 复核 | 执行 session 改完后发起 | 最后 |

并写明：codex 只读共享部分和改动本身，不读第二部分和执行报告。

小改动、补一轮、一次性实验不必用满各节：目标、范围、要改的几处、三到五条判定口径、交回什么，一页以内。写法与交出去前的自查见 [writing-prompts.md](writing-prompts.md)。

## 二、执行

```markdown
# <条目编号> <一句话说清要做什么>

## 1. 身份与职责
你是<一个具体身份，例如"负责 Windows 耐久写入层的资深存储工程师">。这次只负责<范围>。总则：源码是关键中的关键——"实际是什么"只认你亲自读过的源码，每个结论写 `file:line`；注释、TODO、文档、memory 都不是事实来源。

## 2. 背景
- 问题：<大白话，带真实证据>
- 数据支撑：<源码 `file:line`、测试输出、真实数据>
- 用户的决定：<原话或裁定编号>

## 3. 必读材料（绝对路径，开工前全部读完）
- 第一部分共享说明
- 问题总清单条目：<路径> §<条目>
- AGENTS.md 与它指向的 docs/agents/<对应文件>
- 相关裁定 / 方案：<路径与章节>
- 涉及的源码：<模块列表；要求完整读，不读片段>
- 测试矩阵：<skill references/test-matrix.md 路径>，本条适用：<类型>

## 4. 范围与禁止事项
- 只改：<文件列表>
- 不做：兼容层、双轨、兜底、顺手修范围外的问题（范围外发现记进报告）
- 不做 git 写操作；一次性脚本只放 <scratch 路径>
- 不派多个子代理编排分工，自己按下面的步骤做完

## 5. 步骤
1. 先写测试，在**改动前**的代码上确认结果：修 bug 的复现用例必须失败；重构的行为快照必须通过。需要 A/B 的，先跑 A 侧并存档到 <路径>。
2. 按落点全表实现：
   | # | 位置 `file:line` | 现在 | 改成 | 依据 |
   |---|---|---|---|---|
   盘点方法：<grep 了哪些名字、追了哪些调用方>。发现表外落点：列进报告，不自行扩大范围。
3. 第 1 步写的测试不为让实现通过而改；确需改的，在报告里写明理由。
4. 验证：撤回即失败；<A/B 的 B 侧与比对方法>；<对抗测试，逐项>；<平台 / 宿主实测，逐项>。
5. 跑相关检查：改过文件的 compileall、ruff check、ruff format --check、mypy、pyright，加相关单测、`tests/architecture/` 和受影响的集成测试。**不跑完整 `scripts/ci.sh`**：<写明整件事的那一次完整 CI 由哪个 session、在什么时候跑；本 session 若就是最后一个，写"审核修补落地后由本 session 跑一次并存日志">。
6. 执行中查出方案没写到的情况：现有裁定能判的照裁定做，写明裁定号；判不了的选最保守的做法，写进报告"要用户定的事"，不中途停下来问。

## 6. 判定口径
- 正确的样子：<落到具体输入 → 输出>（第 0 步写死的预期表）
- 原则级改动：怎么核"全部落点都改到了"<方法>
- 实际与预期不符：按"预期写错 → 数据造错 → 代码偏离设计 → 设计缺口"的顺序排查。

## 7. 输出格式
报告写到 <路径>：每个落点改了什么（`file:line`）、表外发现、测试在改动前后的结果、对测试的任何改动及理由、每项验证"预期 / 实际 / 过没过 / 证据路径"、跑了哪些相关检查及结果、codex 复核逐条处理结果、要用户定的事。

## 8. 完成标准
- 相关检查与本条测试通过；测试矩阵里本条适用的每一项都有结果和证据，不能确认的单列，写清还差什么
- codex 复核做过一次，每条有处理结果
```

## 三、codex 复核

```markdown
改完后用 codex 只读复核一次（命令见 references/codex-cross-check.md；codex 不可用按那里的回退规则）：
- 只给需求、第一部分共享说明和改动本身（`git diff` 与改后文件），不给执行报告和你的结论。
- 按类别限定范围（对照需求核正确性，跳过风格），不按严重度限定：要它全部报出，每条标严重度（会错数据 / 会卡住 / 只影响报错文字），不要求"只报高危"。
- 原文存档到 <路径>；报告里逐条写处理结果：已修（附相关测试）/ 误报（附源码依据）/ 设计如此（裁定号）/ 记进待办。
- 修完只跑相关测试，不再发起第二轮复核。
```
