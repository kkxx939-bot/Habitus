# 方案评审（`plan` 模式）

在动代码之前，评审一份方案或一条拟定的裁定。方案阶段改，比代码写完再改便宜得多。

## 步骤

### 1. 对齐已有设计

- 列出方案涉及的模块，**完整读这些模块的源码**。不读源码，就不写「这个模块里有什么、怎么取」。
- 列出相关的既有裁定，抄原文。
- 逐条检查：方案和已有裁定冲突吗？冲突的是方案要推翻裁定，还是方案没注意到裁定？
- 方案要解决的问题，既有设计是不是已经解决了？先去既有设计的例子里找。

### 2. 用例子走一遍

方案里每条规则，都用一个具体例子走一遍：

- 正常情况一个
- 按 scenarios.md 的情况矩阵，挑相关的边界情况各一个

每个例子写清：输入是什么、按方案每一步怎么算、最后得到什么、这个结果对用户是否合理。

走不通、或者结果不合理的地方，就是方案的问题。

### 3. 检查问题

- P1 每条规则都能落到具体的代码位置吗？还是只有一句「应该合理处理」？
- P2 有没有写死的时间参数？和时间有关的参数要从数据算，或者交给判断，不能写死。
- P3 方案是否让下游 schema 的大部分字段变空？变空说明层级放错了。
- P4 方案是在打补丁（每一步都在补上一步的洞）吗？是的话停下，回到数据重新想。
- P5 方案依赖的数值（阈值、窗口、次数），是从哪里来的？拍出来的数要标「待定」，并写清怎么定。
- P6 方案改动了哪些已上线的模块？牵扯到未实现模块的，记 TODO 延后。
- P7 方案的验收怎么做？写出验收用的场景和预期。

### 4. 结论

- **可以做**：给出实现时要注意的点。
- **要调整**：每条调整写清改什么、为什么，用第 2 步的例子说明。
- **要重想**：说清方案的根本问题出在哪。

用户确认的结论，原文记进 `裁定.md`（带编号与日期），方案文档原地修改，不追加修改过程。
