# 报告格式

## 单条发现（审核者、复现者用）

```markdown
### <编号> <一句话说清问题>

- **级别**：主流程 / 边角（按 severity.md 的两问）
- **位置**：`file:line`
- **设计依据**：裁定 <编号> / 共享说明 §<章节>
- **输入**：<具体的数据、日子、调用参数>
- **真实输出**：<跑出来的结果，原样贴>
- **设计要求**：<按设计应该是什么>
- **差在哪**：<一句话>
- **怎么确认的**：<复现脚本路径 / 测试名 / 手算过程>
- **确定程度**：确定 / 疑似（疑似要写还差什么才能确认）
```

没有发现问题的检查项，也写一行：

```markdown
- 已查，未见问题：<检查问题编号>，<查了什么、怎么查的>
```

## 汇总表（主会话用）

所有报告回来之后，主会话交叉核对，产出一张表：

| 编号 | 问题 | 报告方 | 复现结论 | 分类 | 级别 | 处理 |
|---|---|---|---|---|---|---|
| R1 | … | 场景对比、codex | 已确认 | 实现偏离设计 | 主流程 | 已修 |
| R2 | … | 读代码 | 复现不出 | 误报 | — | — |
| R3 | … | codex | — | 设计如此（裁定 58） | — | — |

「报告方」一栏能看出不同来源的一致性：只有一方报、另一方明确查过却没报的，要特别核对。

## 问题总清单条目

每条已确认的问题，在问题总清单里写：

```markdown
- [ ] **<编号> <大白话的问题>**
  - 怎么发现的：<哪一步、哪个场景>
  - 怎么确认的：独立复现的输入 → 输出；真实数据证据
  - 修法：<改了什么，`file:line`>
  - 防复发：回归测试 `<文件>::<测试名>`；撤回修复后失败的证据：<报告路径>
  - 修复前后各复现一次：修复前 <结果> / 修复后 <结果>
  - 状态：已确认并已修 / 已确认、要用户定 / 已进待办
  - 用户核查：
```

## 给用户的汇报

按流程逐步讲，每一步写四件事：

```markdown
### 第 2 步：场景预期对比
- 预期：<这一步要验证什么，写死的预期是什么>
- 实际：<跑出来是什么>
- 符不符合：符合 / 不符合
- 不符合的原因：数据问题 / 设计问题 / 实现问题
```

最后两栏：

```markdown
## 主流程
| 问题 | 状态 |
|---|---|
| <用真实数据讲：哪天、几点、哪件事、应该怎样、实际怎样> | 已修 / 要你定（附建议） |

## 边角（已进待办，这一轮不修）
- <一行一条>
```

要用户决定的事，用具体的真实数据讲清楚，并给出建议的改法。不要只摆一张选项表让用户自己挑。
