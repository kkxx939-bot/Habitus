# 写交给另一个 Claude 的提示词

出处与原文摘录见 [writing-prompts-sources.md](writing-prompts-sources.md)。Habitus 的执行 / 审核提示词骨架见 [prompt-template.md](prompt-template.md)，本文件管通用写法与自查。


对方只知道你写进去的东西，你只看得到它交回的报告。官方建议会随新模型变化：动笔前先看当前模型的专页，出处见 [writing-prompts-sources.md](writing-prompts-sources.md)。

## 写什么

1. **只写对方读不到的。** 判断方法：它读代码能找到吗？它会去找吗？两个都是"会"就不写。要写的是：
   - 不在仓库里的决定（用户原话照抄）；
   - 难找的位置（`file:line`，注明核对日期，并说明对不上时以源码为准）；
   - 容易踩的坑；
   - 两种做法都合理而你有偏好时，直接说选哪个。
2. **把完整的任务一次交代清楚，然后让它自己跑。** 包括目标、为什么做、改完是什么样。
3. **规则的原因不明显时，补半句为什么。** 它知道了原因，遇到提示词没写到的情况也能推出该怎么办。
4. **说要它做什么。** 要某种格式或风格时，给 3–5 个正面例子，比列一串"不要"管用。
5. **给能跑出通过或不通过的检查，但只给决定成败的那几条。** 判定口径写成"场景 → 预期"表，每行对应一个测试或一条命令。报告要附命令和输出摘录。条数和每条的耗时照下面"分量要和任务相称"一节来定。
6. **范围写窄写明。** 写清改什么、不改什么，范围外的发现只记不修。新模型会自己扩大任务，所以写上："有更好的做法就用一句话说出来，然后按原要求继续，不要悄悄缩小或扩大；只有几种理解会导致实质不同的工作时，才停下来问。"
7. **有先后顺序的步骤要编号。** 复杂流程给一份清单，让它维护在文件里，并写明完成条件。上下文会被压缩时，要它边做边把进度写进文件。
8. **前后用同一个词指同一个东西。** 引用只给一层，长文件指明看哪一段。
9. **自由度跟风险匹配。** 有多种合理做法时给方向；容易出错、顺序固定的操作（迁移、发布、删除），给确切命令。
10. **写一段防过度工程的话。** 只做要求的和明显必要的；校验只放在系统边界；只用一次的操作不抽 helper；测试是验证正确性的，不是定义答案的，觉得测试错了就报告出来。
11. **报告篇幅按需要。** 写上"覆盖实质内容，不加填充章节和重复总结"，结论放在最前，需要人决定的事单独列出。
12. **项目里每次都一样的规矩，放进一个固定文件让提示词去引用。** 不要每份都重抄。

## 分量要和任务相称

提示词里写了的每一项检查、每一份产物，对方都会照做。多列一项"顺手也查一下"，就是多花对方一段时间。动笔前先回答三个问题，答不上来的不写：

1. **这一步到底改了什么、要回答什么。** 用一两句话写得出来。
2. **最少要看到哪几个数或哪几个结果，才能判它成没成。** 判定口径只列这几条。一个小改动、一次补充，通常三到五条就够。
3. **每一项要跑多久。** 估不出来的先去问或先量；跑得久的要有非做不可的理由。

具体的规矩：

- **只验新加的或改动到的部分。** 补一轮、改一处时，不要求把上一轮的全部检查重跑一遍；只在改动可能波及的地方挑一两条做回归。
- **能用现成的就不重跑。** 已有的盘面、产物、基线能回答的，直接读它；只跑被改的那一步，不为了"完整"把整条流程从头跑。
- **长任务默认不做。** 整段重放、全量基准、跑上几十分钟到几小时的东西，只在这一步的结论确实取决于它时才写进去，并且写明为什么非它不可、只跑一次、用最短的规模。
- **分两段。** 必做的放第一段，做完就写报告交回；可有可无的对照、额外的数据集、复核、抽查放第二段，写明"等看过第一段再决定做不做"，或者干脆不写。
- **下一步不需要的产物不要等。** 写清楚下游要用的是哪几样，别的可以后做或不做（例如下游只读结构化的答案，就不必等给人看的文字生成完）。
- **给一个时间上的预期。** 写上"这一步大致该在多久内交回；超了就先交已有的结果并说明还差什么"。

## 删掉这些（对当前模型无效或有害）

- 大写、加粗堆砌、"必须""务必"：会让模型过度套用这条规则。
- "仔细""想清楚""认真""think hard"：思考深度由 effort 控制，这些词只是普通文字。
- 泛泛的"做完要验证""double-check""re-verify""派子代理复核你的工作"：当前模型会自己验证，加这些只会过度验证、浪费 token。要的是具体的检查（第 5 条），不是叫它"再查一遍"。
- "把你的推理过程完整写出来"：可能被拒（`reasoning_extraction`）。要的话，就要一个简短解释或操作摘要。
- "keep going / don't be lazy / 一定要做完"：容易让它过度工作。要的话，就给完成条件和清单。

## 子代理 brief

- **先判断值不值得派。** 只派大块的、真正独立、能并行的工作，或者需要一个没看过你推理过程的审查者。几次工具调用就能做完的，自己做。能一个子代理做完的，不派多个。
- **小任务写清四件事**：
  1. 要回答什么、为什么问；
  2. 已知和已排除的；
  3. 从哪查、能不能改文件；
  4. 交回什么格式、多长。
- **大任务**：Habitus 的执行提示词骨架见 [prompt-template.md](prompt-template.md)，共享说明见 [brief-template.md](brief-template.md)，codex 审核那一段也在 prompt-template 里。本文件只管写法与自查。

## 交出去之前自查

- [ ] 路径、行号、前提都在现场核过，没有凭记忆写的
- [ ] 写的都是对方读不到的，没有重复规矩文件
- [ ] 原因不明显的规则带了半句为什么
- [ ] "删掉这些"一节列的东西都不在里面
- [ ] 判定口径每一行都能跑出通过或不通过
- [ ] 判定口径只有决定成败的几条；拿掉任何一条，都会说不清这一步成没成
- [ ] 没有要求重跑上一轮已经过了的检查；没有可以用现成产物代替的重跑
- [ ] 每一项长任务都写了非做不可的理由；可有可无的已经删掉或放进第二段
- [ ] 写了大致该多久交回、超时怎么办
- [ ] 范围、禁止事项、什么时候停下来问，都写了
- [ ] 前后用词一致
- [ ] 读者测试：一个没参加讨论的工程师，只拿到这份提示词，能不能照着做下去？

## 规则反复被漏掉时

不能有例外的规则，交给测试、CI、lint、钩子、权限规则去执行，不在提示词里加重语气。只是偏好的事，不要做成硬检查。看对方实际怎么执行：同一处纠正两次还不对，就重写提示词。
