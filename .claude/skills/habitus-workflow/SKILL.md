# Habitus 工作流程：执行与审核

## 概述

这个 skill 规定在 Habitus 里**怎么做一条改动**，以及**怎么审核代码和方案**。它要解决反复出现的五个问题：

1. **结论不对着源码。** 凭文档、注释、TODO、memory、子代理转述下结论，报出来的问题有不少是假的，定下的方案落不到代码上。
2. **伤害最大的 bug 不是读代码读出来的。** 2026-10-30 的两个主流程问题，几轮多团队审核都没发现，最后是在**写下场景预期、再拿代码跑出来对比**时暴露的。
3. **报上来的问题里有不少是误报。** 不复现就修，会把对的代码改坏。
4. **子代理没有统一的正确认知，结论就会偏离设计。**
5. **靠人设不靠流程。** 让同一个模型扮演架构师、测试、审核员，盲点不会变；严谨要靠"每一步做完接什么、谁做、做哪种测试、过闸条件是什么"写死。

## 总则：源码是关键中的关键

| 规则 | 含义 |
|---|---|
| **"应该是什么"看设计，"实际是什么"只看源码** | 对不对，对照裁定原文和方案文档判断；代码现在怎么做、某个模块里有什么、谁调用谁，只认本次亲自读过的源码。后面的裁定覆盖前面的。 |
| **每一句"是什么"都带 `file:line`** | 落点、预期依据、问题描述、报告结论，凡是说代码怎样，都要写出本次读过的 `file:line`（带函数名，行号会漂移）。写不出来的，就是没核过，不许写成事实。 |
| **这些都不是事实来源** | 代码注释、TODO、docstring 里的"设计如此"、README、memory、旧报告、子代理或 codex 的转述。它们只能当线索，用之前回源码核。 |
| **写设计之前读完整个模块** | 写"某模块里有什么、怎么取"之前，完整读这个模块的源码，不读片段。 |
| **改原则之前先盘点全部落点** | grep 名字、调用方、配置键、测试、文档，逐个列 `file:line` 和每处怎么改；找不全不派人。 |
| **测试跑的是真实代码路径** | 不拆一半跑；涉及模型的按需用确定性替身或真实模型（见测试矩阵），但链路本身是源码里那条。 |
| **先有预期，再看结果** | 预期写死、存盘，再去跑。 |
| **只报确认过的** | 只报有"具体输入 → 真实输出 → 和设计差在哪"的问题。 |
| **按检查维度分工，不按人设分工** | 想要另一种视角，换一个模型（codex），不换人设。 |
| **主流程优先** | 先判会不会影响主流程，再决定这一轮修不修。 |

## 何时使用

| 模式 | 用在什么时候 | 走哪些步骤 |
|---|---|---|
| `change <清单条目>` | **执行一条改动**（例如 38 号清单的 W 条目、一个新功能、一次重构） | 执行流程 0 → 5，第 4 步调用审核流程 |
| `review <范围>` | 一批改动写完、准备交给用户之前 | 审核流程全部步骤 |
| `fix <问题号>` | **每一个修复**落地时 | 审核流程 0 → 1 → 2 → 5 → 7 → 8 |
| `audit <模块>` | 给一个模块或一整层做全面体检 | 审核流程全部步骤 |
| `deepen <题目>` | 用户提出新方向或新题目时，**写方案、改题目、派人之前**先把题目问深（更深，不是更大） | [references/deepen-topic.md](references/deepen-topic.md)，确认后接 `plan` 或 `change` |
| `plan <方案文档>` | 动代码之前评审一份方案或一条拟定的裁定 | [references/plan-review.md](references/plan-review.md) |

改错别字、改日志措辞这类不改变任何行为的改动，用内置的 `/code-review low` 就够了。

## 执行流程（`change` 模式）

一条改动走 6 步，每步有闸，闸不过不进下一步。阶段内部自动往下走，只在**阶段边界**停下来给用户看结果。

| 步 | 谁做 | 做什么 | 过闸条件 |
|---|---|---|---|
| **0 立项** | 主 session | ① 写清问题和数据支撑（真实证据，带源码 `file:line`）；② **读完涉及的模块，盘点全部落点**（`file:line` + 每处怎么改 + 怎么找全的）；③ **先写死预期**（落到具体输入和输出）；④ 按 [references/test-matrix.md](references/test-matrix.md) 选测试；⑤ 按 [references/brief-template.md](references/brief-template.md) 写共享说明，按 [references/prompt-template.md](references/prompt-template.md) 写执行提示词和测试工程师提示词 | 落点全表、预期、测试计划都已存盘 |
| **1 建基线** | **测试工程师**（单独 session，只拿共享说明和症状，不拿实现思路） | 在**改动前**的代码上：跑 `scripts/ci.sh`；写本条要用的测试并确认它们在旧代码上的结果（修 bug：复现用例必须失败；重构：行为快照必须通过）；跑 A/B 的 **A 侧**并存档产物；记下基线代码的 commit 或 `git archive` 只读副本位置 | 基线测试、A 侧产物、基线 CI 结果都存档 |
| **2 实现** | 实现 session | 按执行提示词改；**不许改测试工程师写的测试**，确需改动的在报告里写明理由，由第 3 步复核 | `scripts/ci.sh` 全绿 |
| **3 验证** | **测试工程师**（另开 session，不读实现者的自评） | 回归；**撤回即失败**；**A/B 对照**；**对抗测试**；平台相关的跑三平台 CI 或真实宿主实测。具体做哪些按测试矩阵 | 矩阵里这一类要求的每一项都过，结果存档 |
| **4 审核** | 另开 session，审核流程 `fix` 或 `review` | 场景预期对比、对照设计读源码、codex 复核、独立复现 | 没有已确认的主流程问题；有就回第 2 步，修复再走一遍 3、4 |
| **5 收口** | 主 session | 对着设计和源码核各方报告；问题总清单补"修复前后各复现一次"的结果和状态；到阶段边界时按 [references/report-format.md](references/report-format.md) 的"给用户的汇报"逐步讲 | 用户看过（阶段边界） |

**每一步开跑前主 session 重核下一份提示词**：第 3 步的提示词写于实现之前，第 2 步结束后主 session 先读 `git diff` 和改后的文件，把行号换成改后的、按实际改动补检查项（例如锁文件逐包对比），并写明"不要读实现报告"，再交给测试工程师；后一条的提示词要在前一条改完的代码上重读源码再写。

**为什么测试工程师和实现者分开**：同一个人写实现又写测试，测试会不自觉地贴着实现写，守不住行为。基线必须在改动之前建，A 侧产物必须来自改动前的代码。

## 审核流程（`review` / `fix` / `audit`）

```
0 定范围 → 1 共享说明 → 2 场景预期对比 ─┐
                       3 对照设计读源码 ─┼→ 5 汇总与独立复现 → 6 分级 → 7 修复与防复发 → 8 收口
                       4 跨模型复核 ────┘
```

2、3、4 三步可以并行，但都要等第 1 步写完。

### 第 0 步：定范围

- 写出审哪些文件，以及它们对应哪些设计点（裁定编号、方案章节）。
- 用 `git status` / `git diff` 看改动。工作区里有你没改过的改动，先问用户，那可能是别的会话正在改的。
- 对照 `待办.md` 和问题总清单，列出**已知、不重报**的事项。
- **原则级改动先盘点全部落点**（规则同总则）。审核中又发现盘点之外的落点，先停下补全盘点、更新说明，再继续。

**出口条件**：一张「文件 → 设计点」对照表；原则级改动还要有完整的落点清单。

### 第 1 步：写共享说明

按 [references/brief-template.md](references/brief-template.md) 写：这次审什么；设计怎么说（**抄裁定原文和编号**）；正确的样子；容易读错的地方；已经定了、不要再报的；规则与报告格式。这一层已有统一说明（例如 `39-预测层统一说明.md`）的，直接引用章节，只补本次特有的部分。

**出口条件**：说明写完、存盘。说明没写完，不派任何人。

### 第 2 步：场景预期对比（最重要的一步）

按 [references/scenarios.md](references/scenarios.md)：每个设计点找场景，没有就按情况矩阵补；**先写死预期**，再跑真实代码；逐个对比，不一致的先查预期、再查数据、再查代码、最后才是设计缺口。

**出口条件**：一张「设计点 → 场景 → 预期 → 实际 → 一致吗」的表；没有场景的设计点单独标出。

### 第 3 步：对照设计读源码

按 [references/checklist.md](references/checklist.md) 的检查问题读。派子代理时**按检查维度拆**：设计一致性、工程正确性、测试有没有守住（变异测试）、没人调用的代码、架构边界。每个子代理只拿共享说明、它负责的检查问题、文件范围。每个结论带 `file:line`。

### 第 4 步：跨模型复核

用 codex 拿同一份共享说明独立审一遍，命令见 [references/codex-cross-check.md](references/codex-cross-check.md)。不给它看 Claude 这边的任何结论。只关心两边不一致的地方。**codex 额度用完或不可用时不等**：立刻换本机 Claude Code CLI 的 sonnet 4.5 只读复核，报告写明换了模型；阶段边界前 codex 恢复了就补做一次，没恢复就在汇报里写明（细则同一文件）。

### 第 5 步：汇总与独立复现

1. **等第 2、3、4 步全部回来**再汇总。
2. 合并重复项，分成：疑似问题 / 设计如此（注明裁定号）/ 已知已排期（注明待办条目）。
3. 每条疑似问题交给**独立复现者**：只拿症状和设计，不拿任何人的诊断和疑似行号；自己写最小复现，给出真实输出。
4. 主会话对着共享说明和源码核对，分成：**已确认 / 误报 / 设计如此**。

### 第 6 步：分级

用两问分级（[references/severity.md](references/severity.md)）：正常用户第一个月会不会碰到？碰到之后会不会自己恢复？会碰到且不会恢复的是**主流程**，这一轮修；其余是**边角**，记进 `待办.md`。

### 第 7 步：修复与防复发

- **会改变设计或产品行为的**，先停下来问用户：用真实数据讲清问题，给出建议改法。用户定了，记进裁定，再改代码。
- 纯实现错误直接修。修复者只拿**主会话核过的复现结论**。
- 每个修复都有回归测试，并证明**撤回修复后这条测试会失败**。
- 修复也是新改动，用 `fix` 模式再走一遍。
- 不保留兼容层、不留双轨、不堆兜底。

### 第 8 步：收口

1. 改动不小或还在确认出新问题，就再审一轮，直到某一轮确认不出新的主流程问题。
2. 本地跑通 `bash scripts/ci.sh`。
3. 每条问题按 [references/report-format.md](references/report-format.md) 记进问题总清单。
4. 按"给用户的汇报"格式逐步讲；问题分"主流程"和"边角"两栏。

## 参与者之间的隔离

| 角色 | 拿什么 | 不拿什么 |
|---|---|---|
| 测试工程师（建基线） | 共享说明、症状、预期、测试计划 | 实现思路、执行提示词 |
| 实现者 | 执行提示词、共享说明、落点全表 | 别的修法建议 |
| 测试工程师（验证） | 改动、共享说明、测试计划、基线存档 | 实现者的自评 |
| 场景与读源码的审核者 | 共享说明、检查问题、文件范围 | 别的审核者的报告 |
| codex 复核 | 共享说明、文件范围 | Claude 这边的任何结论 |
| 复现者 | 症状 + 设计 | 任何人的诊断、疑似原因的行号 |
| 修复者 | 主会话核过的复现结论 | 别人的修法建议 |

不把一个子代理的报告路径交给另一个子代理读。子代理不得改共享说明；发现说明和裁定或源码对不上，写进报告，由主会话核过再改。

## 红线

| 想这么做的时候 | 为什么不行 |
|---|---|
| 「文档 / 注释 / memory 里写了它是这样的」 | 不是事实来源。回源码核，写出 `file:line`。 |
| 「这个模块我大概知道里面有什么」 | 没读完就不写。读完整个模块再写设计。 |
| 「子代理说第 N 行有问题」 | 自己打开那一行看，再独立复现。 |
| 「代码读了好几遍，没问题」 | 没跑场景，就不算审过。 |
| 「先跑一遍，看看结果再说对不对」 | 预期必须先写。 |
| 「改完了再补测试」 | 基线和测试在改动前由测试工程师建。改完再补的测试只会贴着实现写。 |
| 「实现者顺手把测试也改了，CI 绿了」 | 实现者不改测试工程师的测试；改了要写理由并复核。 |
| 「修好了，CI 绿了」 | 还要撤回即失败，并用 `fix` 模式过一遍影响面。 |
| 「重构没改行为，不用 A/B」 | 没有 A/B 对照，"没改行为"只是自称。 |
| 「这个子代理报的问题很具体，直接修吧」 | 具体不等于真实。没独立复现，就不算确认。 |
| 「顺手把这个边角问题也修了」 | 边角进待办。 |
| 「给子代理讲一下背景就行」 | 必须读同一份存了盘的说明。 |
| 「多派几个角色，审得更全」 | 换人设盲点不变。要换视角就换模型，要更全就补检查问题、场景和测试。 |
| 「这个之前报过吗？不确定，再报一次」 | 先查 `待办.md` 和问题总清单。已排期的说成已排期。 |
| 「改的是一条原则，先告诉修复者最明显的两处」 | 先盘点全部落点，再派人。 |
| 「审出一处漏改的，补上就行」 | 说明盘点不完整，先补全盘点。 |
