# 检查问题清单

第 3 步「对照设计读代码」用。按维度分工，每个维度是一组要回答的问题。派子代理时，一个子代理负责一个或几个维度。规模小的改动可以由主会话一人走完。

每个问题都要回答「是 / 否 / 不适用」，答「否」的就要给出证据。

## A. 设计一致性

- A1 每个设计点，代码实际怎么做？逐条写出「设计说 X，代码做 Y，位置 `file:line`」。
- A2 有没有设计里没有、代码里却有的行为？例如多出来的过滤、兜底、默认值。
- A3 兜底逻辑是否符合设计？拿前一天的数据顶替今天这类兜底，会让预测错，必须有设计依据。
- A4 「没看到」和「没做」、「自然发生」和「提醒后发生」这类设计里区分开的概念，代码里是否也区分开了？
- A5 同一条上游记录，会不会被两个消费者读成两种事实？

## B. 工程正确性

- B1 边界：空集、只有一个样本、并列、刚好等于阈值。
- B2 时间：跨零点、夜批前后、时区、本地时间和偏移、日期换算。
- B3 错误路径：失败会不会被吞掉？重试会不会重复写？
- B4 崩溃恢复：在任意一步崩溃后重启，状态是否一致？持久化写入是否原子？
- B5 并发：两个 worker 或两次触发同时跑，会不会重复建、重复结算？
- B6 幂等：同一输入跑两次，结果是否相同？「结算完的日子不再改」之类的不变量是否成立？

## C. 测试有没有守住

- C1 改动涉及的每个分支，都有测试覆盖吗？
- C2 **变异测试**：在 scratch 里把关键分支或修复改坏（monkeypatch、替换函数、改模块副本），相关测试会不会失败？改坏了还全绿的，就是缺口。
- C3 测试断言的是行为，还是实现细节？只断言「被调用过」的测试守不住行为。
- C4 测试数据是否构成了它声称要测的情况？

## D. 没人调用

- D1 新增或改动的函数，有生产代码调用吗？只被测试调用的算死代码。
- D2 配置里新增的字段，有地方读吗？
- D3 注册了的分支（handler、类型、路由），有地方分发到吗？
- 用 grep 加入口追踪确认，不要只靠工具报告。

## E. 架构边界

- E1 依赖方向符合 `tests/architecture/` 和 `AGENTS.md` 的约束吗？
- E2 宿主相关的知识，是否只出现在适配器和 harness 定义里？
- E3 有没有同一个概念在两处各有一套实现？
- E4 被取代的旧代码删干净了吗？有没有留别名或转发模块？

## F. 修复的影响面（`fix` 模式必查）

- F1 这个修复改变了哪些函数的行为？列出它们的所有调用方。
- F2 每个调用方依赖的不变量，修复后还成立吗？
- F3 修复有没有把之前修过的问题带回来？对照问题总清单里同一模块的已修条目，逐条确认。
- F4 修复引入的新时序、新状态，在跨零点、夜批前后、崩溃重启时是否正确？
- F5 原则级改动：说明里的落点清单找全了吗？自己再 grep 一遍相关的名字、调用方、配置键、测试和文档，列出清单之外、同样受这条原则约束的位置。找到任何一处，都按「盘点不完整」报，不按单个漏改报。

## 不在本清单里的

- 命名、格式、注释措辞：不报。
- 「可以更优雅」「建议抽象」：不报，除非它造成了 E3 那样的重复实现。
- 性能：只报真实数据规模下会出问题的。
