# Habitus 代码审核

## 概述

这个 skill 规定在 Habitus 里怎么审核代码和方案。它要解决三个反复出现的问题：

1. **伤害最大的 bug 不是读代码读出来的。** 2026-10-30 的两个主流程问题（「天天做的事漏过一次，以后单独漏一天就不再提醒」「零点建预期用的是前一晚的旧表」），之前几轮多团队全面审核都没发现，最后都是在**写下场景预期、再拿代码跑出来对比**时暴露的。
2. **报上来的问题里有不少是误报。** 不复现就修，会把对的代码改坏。
3. **子代理没有统一的正确认知，结论就会偏离设计。** 例如把「没看到他做」当成「他没做」，而设计里这两件事是分开的。

所以本流程把**场景预期对比**放在读代码前面，把**独立复现**放在修复前面，把**共享说明**放在派任何人之前。

## 核心原则

| 原则 | 含义 |
|---|---|
| **设计是唯一标尺** | 「对不对」只对照裁定原文和方案文档来判断。代码注释、TODO、子代理的推理都不是依据。后面的裁定覆盖前面的。 |
| **先有预期，再看结果** | 任何场景都要先把「应该发生什么」写死，再去跑。跑完再补的预期没有判别力。 |
| **确定问题，不是发现问题** | 只报有「具体输入 → 真实输出 → 和设计差在哪」的问题。确认不了的单列，不计数。 |
| **一份说明，所有人读** | 共享说明由主会话对着裁定写，不收任何子代理的结论。 |
| **按检查维度分工，不按人设分工** | 分工依据是「回答哪组检查问题、拿哪些材料」，不是「扮演什么角色」。想要另一种视角，就换一个模型（codex），不要换一个人设。 |
| **主流程优先** | 先判这个问题会不会影响主流程，再决定修不修。边角问题记进待办，以后迭代修。 |

## 何时使用

| 模式 | 用在什么时候 | 规模 |
|---|---|---|
| `change <范围>` | 一批改动写完、准备交给用户之前；范围可以是工作区改动、某几个文件、某个包 | 中 |
| `fix <问题号>` | **每一个修复**落地时，尤其是主流程上的修复。修复本身是新改动，会带出回归 | 小 |
| `audit <模块>` | 给一个模块或一整层做全面体检，例如 README 核对那样的逐段检查 | 大 |
| `plan <方案文档>` | 动代码之前评审一份方案或一条拟定的裁定 | 中 |

**不需要用这个 skill 的情况**：改错别字、改日志措辞这类不会改变任何行为的改动，用内置的 `/code-review low` 就够了。

## 流程

按规模裁剪：`fix` 模式只走 0 → 1 → 2 → 5 → 7 → 8；`plan` 模式见 [references/plan-review.md](references/plan-review.md)；其余模式走全部步骤。

```
0 定范围 → 1 共享说明 → 2 场景预期对比 ─┐
                       3 对照设计读代码 ─┼→ 5 汇总与独立复现 → 6 分级 → 7 修复与防复发 → 8 收口
                       4 跨模型复核 ────┘
```

2、3、4 三步可以并行，但都要等第 1 步写完。

### 第 0 步：定范围

- 写出这次审的是哪些文件（`file` 列表），以及它们对应哪些设计点（裁定编号、方案章节）。
- 用 `git status` / `git diff` 看改动。工作区里有你没改过的改动，先问用户，那可能是别的会话正在改的。
- 对照 `待办.md` 和问题总清单，列出**已知、不重报**的事项。

**原则级改动先做盘点。** 如果这次改动或修复是一条原则，例如「夜批改成一条线性链」「所有预期都在零点建」「X 一律从 Y 取」，那么在写说明、派修复者之前，主会话必须先找全这条原则在代码里的**所有落点**：grep 相关的名字、调用方、配置、测试、文档，逐个列出 `file:line`，并标明每处要怎么改。不能只点名最先想到的两三处，剩下的交给修复者去发现，否则修一轮、审出漏的、再修一轮，会变成连续打补丁。

- 盘点结果写进共享说明第 1 段，作为修复和审核的共同范围。
- 审核时要单独检查盘点是否找全了：有没有漏掉的落点（见 checklist F5）。
- 审核中又发现盘点之外的落点，说明盘点没做完。先停下补全盘点、更新说明，再继续，不要只把这一处补上。

**出口条件**：有一张「文件 → 设计点」对照表；原则级改动还要有一张完整的落点清单。

### 第 1 步：写共享说明

按 [references/brief-template.md](references/brief-template.md) 写，固定这几段：

1. 这次审什么、为什么审
2. 设计怎么说：**抄裁定原文和编号**，不要转述
3. 正确的样子：每个设计点在具体数据上应该表现成什么样
4. 容易读错的地方（例如「没看到 ≠ 没做」「提醒后才做的不算他的规律」）
5. 已经定了、不要再报的事
6. 规则与报告格式

如果这一层已经有统一说明（例如预测层的 `39-预测层统一说明.md`），直接引用它的章节，只补本次特有的部分。

**出口条件**：说明写完、存盘。说明没写完，不派任何人。

### 第 2 步：场景预期对比（最重要的一步）

按 [references/scenarios.md](references/scenarios.md) 做：

1. 对第 0 步的每个设计点，找出覆盖它的场景，可以是测试、回放 case 或手算小例子。
2. 没有场景覆盖的设计点，按「情况矩阵」补场景，例如天天做、漏一天、连漏、停很久再回来、换了时间、节假日、整天没会话。
3. **先把每个场景的预期结果写死**（第几天、几点、应该发生什么），再跑代码。
4. 逐个对比预期和实际。不一致的，先查是预期写错了还是代码错了。

**出口条件**：一张「设计点 → 场景 → 预期 → 实际 → 一致吗」的表。没有场景的设计点要单独标出来。

### 第 3 步：对照设计读代码

按 [references/checklist.md](references/checklist.md) 里的检查问题清单读。需要派子代理时，**按检查维度拆**：

- 设计一致性：代码实际怎么做，和设计逐条对比
- 工程正确性：边界、错误路径、崩溃恢复、持久化原子性、时区
- 测试有没有守住：做变异测试，把修复或关键分支改坏，看测试会不会失败
- 没人调用的代码、配置里定义了却没接上的字段
- 架构边界：依赖方向、「一条记录一个解释」

每个子代理拿到的东西只有：共享说明、它负责的检查问题、文件范围。

### 第 4 步：跨模型复核

用 codex 拿**同一份共享说明**独立审一遍，命令见 [references/codex-cross-check.md](references/codex-cross-check.md)。**不给它看 Claude 这边的任何结论。**

只关心两边结论**不一致**的地方：一边报了另一边没报的，或者两边对同一处的判断相反。

### 第 5 步：汇总与独立复现

1. **等第 2、3、4 步全部回来**，再汇总。不要回来一份转述一份。
2. 合并重复项，然后逐条分成：疑似问题 / 设计如此（注明裁定号）/ 已知已排期（注明待办条目）。
3. 每条疑似问题交给一个**独立复现者**。复现者只拿**症状和设计**，不拿任何人的诊断，也不拿疑似原因的代码行号。复现者自己写最小复现，给出真实输出，并判断它是否偏离设计。
4. 主会话对着共享说明核对复现结论，最后分成三类：**已确认 / 误报 / 设计如此**。

### 第 6 步：分级

每条已确认的问题，用两个问题来分级（详见 [references/severity.md](references/severity.md)）：

- **正常用户在第一个月会不会碰到？**
- **碰到之后，会不会自己恢复？**

会碰到且不会自己恢复的，算**主流程**，这一轮修。其余的算**边角**，记进 `待办.md` 一行，以后迭代修，不为它开新的核对轮。

### 第 7 步：修复与防复发

- **会改变设计或产品行为的**，先停下来问用户：用真实数据讲清问题，并给出建议的改法。用户定了以后，记进 `裁定.md`，再改代码。
- 纯实现错误，直接修。修复者只拿**主会话核过的复现结论**，不拿别人的修法建议。
- 每个修复都要有回归测试，并且证明**撤回修复后这条测试会失败**。
- 修复也是新改动，要用 `fix` 模式再走一遍：查影响面，重跑相关场景。
- 不保留兼容层。项目还没上线，被取代的代码直接删掉。

### 第 8 步：收口

1. 这一轮改动不小，或者还在不断确认出新问题，就再审一轮。直到某一轮再也确认不出新的主流程问题，才算结束。
2. 本地跑通 `bash scripts/ci.sh` 整条链。
3. 每条问题记进问题总清单，格式见 [references/report-format.md](references/report-format.md)。
4. 按 [references/report-format.md](references/report-format.md) 的「给用户的汇报」格式汇报：按流程逐步讲每一步的预期、实际、是否一致；问题分成「主流程（已修 / 要你定）」和「边角（已进待办）」两栏。

## 参与者之间的隔离

| 角色 | 拿什么 | 不拿什么 |
|---|---|---|
| 场景与读代码的审核者 | 共享说明、检查问题、文件范围 | 别的审核者的报告 |
| codex 复核 | 共享说明、文件范围 | Claude 这边的任何结论 |
| 复现者 | 症状 + 设计 | 任何人的诊断、疑似原因的行号 |
| 修复者 | 主会话核过的复现结论 | 别人的修法建议 |
| 修复后的审核者 | 改动 + 共享说明 | 修复者的自评 |

不要把一个子代理的报告路径交给另一个子代理去读。子代理不得改共享说明；发现说明和裁定或源码对不上的，写进报告，由主会话核过再改。

## 红线

| 想这么做的时候 | 为什么不行 |
|---|---|
| 「代码读了好几遍，没问题」 | 读代码查不出「算法在某种日子规律下的行为不符合设计」。没跑场景，就不算审过。 |
| 「先跑一遍，看看结果再说对不对」 | 跑完再定的预期，会不自觉地向实际结果靠拢。预期必须先写。 |
| 「这个子代理报的问题很具体，直接修吧」 | 具体不等于真实。没经过独立复现，就不算确认。 |
| 「顺手把这个边角问题也修了」 | 边角进待办。顺手修会扩大改动面，而且这次修改本身没人审。 |
| 「修好了，CI 绿了」 | 还要证明撤回修复后测试会失败，并且用 `fix` 模式过一遍影响面。 |
| 「给子代理讲一下背景就行」 | 口头讲的背景每次都不一样。必须读同一份存了盘的说明。 |
| 「多派几个角色，审得更全」 | 同一个模型换人设，盲点不会变。要换视角就换模型，要更全就补检查问题和场景。 |
| 「这条注释说它是这么设计的」 | 注释和 TODO 记的是当时的想法。以裁定和代码为准。 |
| 「这个之前报过吗？不确定，再报一次」 | 先查 `待办.md` 和问题总清单。已排期的说成已排期。 |
| 「改的是一条原则，先把最明显的两处告诉修复者，其他的它会找到」 | 修复者只会改你点名的地方。漏掉的落点会在下一轮审核里冒出来，变成连续打补丁。原则级改动先盘点全部落点，再派人。 |
| 「审出一处漏改的，补上就行」 | 一处漏改说明盘点不完整，很可能还有别处。先补全盘点，再一起改。 |

## 产物与路径

| 产物 | 位置 |
|---|---|
| 共享说明、复现脚本、变异测试、各方报告 | scratchpad 下 `review/<日期>-<范围>/` |
| 报告原文归档 | `~/Desktop/Habitus实验数据/事件融合与词表重做/37-材料/` 下按轮次分目录，不覆盖旧报告 |
| 问题总清单 | `~/Desktop/38-README核对问题清单.md`（新一轮审核开一节；用户另行指定的，以用户为准） |
| 设计决定 | `~/Desktop/Habitus实验数据/事件融合与词表重做/裁定.md`（编号接着往下排） |
| 边角与范围外的发现 | 同目录 `待办.md` |

一次性脚本不进仓库。git 操作全部由用户自己做。
